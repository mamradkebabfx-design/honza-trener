## Running locally

Serving the static files is enough for everything except the contact form:

```
python3 -m http.server 8000
# then open http://localhost:8000
```

`file://` breaks relative paths and `localStorage`, so always serve over HTTP. **The contact form (`/api/contact`) won't work under `python3 -m http.server`** — that endpoint only exists when the Vercel runtime is serving the repo. For local end-to-end form testing, use `npx vercel dev` (no install needed), which boots a local replica of the Vercel edge + serverless functions and loads env vars from a local `.env` file if present. Without `vercel dev`, test the form on the deployed Vercel URL.

**`script.js`/`styles.css` caching gotcha with `python3 -m http.server`:** Python's SimpleHTTPServer sends `Last-Modified` but no `Cache-Control`, so Chrome's disk cache can keep serving a stale `script.js` **or `styles.css`** even after a normal reload or after navigating with a cache-busting query string on the *page* URL — a `<script src="script.js">` or `<link rel="stylesheet" href="styles.css">` sub-resource request is unaffected by a query string on the page's own URL, since that only busts the document itself. Symptom for JS: edited code silently doesn't run, zero console errors. Symptom for CSS (confirmed 2026-09-07 during the dark-theme rewrite): edited styles don't show up even after several page reloads with `?v=...` cache-busting, even though the file on disk is correct — `fetch('/styles.css', {cache:'no-store'})` confirms the server is serving the new content, it's purely a stale browser cache of the sub-resource. **Fix: hard reload (Cmd+Shift+R), not a normal refresh**, whenever testing a `script.js` or `styles.css` change locally — a page-URL query string alone does not reliably bust either. This is a local-dev-only issue — Vercel/CDN cache invalidates correctly per deploy, so it doesn't affect production.

## Dark theme (2026-09-07)

The whole site (`index.html` + `privacy-policy.html`, both share `styles.css`) was converted from a light theme (white/`--bg-alt` sections alternating, dark `.hero`/`.forwhom`/`.cta` as bookends) to dark throughout. This took several iterations in one session — worth knowing the reasoning if it's ever revisited:

- **New tokens added to `:root`, old ones left untouched**: `--dark-bg`, `--dark-bg-alt`, `--card-dark`, `--text`, `--text-2`, `--text-muted`, `--dark-line`. The original `--bg` (`#fff`), `--bg-alt` (`#f6f7f8`), `--ink`, `--ink-2`, `--muted`, `--line` were **deliberately kept at their original light-theme values** — they're still used, unchanged, by two intentional light "island" surfaces: `.cta__form` (the contact form) and `.booking-modal__box` (the Google Calendar modal). Both stay white/light because they're functional form UI where light-on-white is the most legible/usable choice — this mirrors how `.cta__form` already floated as a white card on the dark `.cta` section even in the old light theme, so it's not a new pattern, just now more visually distinct against a dark page.
- **`--dark-bg` and `--dark-bg-alt` are currently the same value** (`#0f1113`, same as `--ink`) — i.e. **every section on the page has the exact same background color**, on purpose. Earlier attempts used slightly different tones per section (mimicking the old light-theme's white/`--bg-alt` alternation) but this repeatedly produced a visible hard seam at section boundaries (flagged by the user twice — "vidíš ten rozdíl mezi barvama, to je fakt ošklivé"). Making every section literally identical removes the seam by construction. `--card-dark` (`#1a1d1f`) is the one deliberately *lighter* tone, used only for bounded card/node surfaces (`.step`, `.plan`, `.timeline__node`) — that's fine because those are bordered shapes, not full-bleed section backgrounds, so they don't create the same seam problem.
- **Two real "light-on-light"/"dark-on-dark" bugs were fixed while converting** — worth remembering if new UI is added inside the light islands, or if any element still uses `background:var(--ink)` for a solid fill:
  1. `.btn--primary`, `.btn--small`, and `.sticky-cta` used to be `background:var(--ink);color:#fff` (a near-black button, since the page around it was white). Once the page itself became dark, a near-black button became nearly invisible against it. Fixed by switching these to `background:var(--accent)` instead — this is now the single "solid CTA fill" color everywhere, not `--ink`.
  2. Elements inside the light islands that didn't have their own explicit text color were silently inheriting the new dark-theme `color:var(--text)` (near-white) from `body`/`h1,h2,h3`, becoming invisible against the islands' white background — specifically `.booking-modal__head h2` and `.field input`/`.field textarea` (typed text was invisible while typing). - `.top-nav`/`.nav`/`.nav--solid`'s "scrolled"/solid state changed from `background:rgba(255,255,255,.85)` (white) to `rgba(15,17,19,.85)` (dark), and the text-color-darkens-on-scroll rules were removed/repointed to `var(--text)`/`var(--text-2)` — text now stays light in both the transparent-over-hero and scrolled states, since the whole page is dark now. ## Reveal animations (extended 2026-09-07)

`script.js` now has **two** IntersectionObservers instead of one:
- `io` — the original one-time reveal (`.reveal:not([data-reveal="repeat"])`): adds `.visible` once and never removes it.
- `ioRepeat` — new, for `[data-reveal="repeat"]` elements: **toggles** `.visible` on every intersection change, so the animation replays every time the element scrolls back into view (added because the user wanted `.forwhom__item`s and the `.timeline` to re-animate on scrolling back up, not just once).

Two different stagger patterns are in use, depending on whether the staggered elements sit at the same scroll position or not:
- **`.forwhom__item`s** are all in one row (same vertical position), so each item independently gets `data-reveal="repeat"` and its own `--reveal-delay` custom property via `:nth-child()`, and `.forwhom__item.reveal{transition-delay:var(--reveal-delay,0s)}` staggers them — this works because the IntersectionObserver fires for all 3 at essentially the same scroll moment.
- **`.timeline`'s 8 node/content children are *not* at the same vertical position** (they're split across the grid's top/middle/bottom rows — see above), so observing them individually made them reveal in row order (top-row items, then nodes, then bottom-row items) instead of 1→2→3→4, which the user flagged as "na přeskáčku". **Fixed by observing only the `.timeline` container itself** (`class="timeline reveal" data-reveal="repeat"`) — `.timeline.reveal{opacity:1;transform:none}` cancels the container's own visual reveal (it's only used as the trigger), and the children (`.timeline__node`, `.timeline__content`) carry their own `opacity:0`/transform + `transition-delay` (via the same `:nth-child()` pairing used for grid placement), gated on `.timeline.visible` being present on the ancestor. **If another multi-row/multi-position staggered group is ever built, use this container-trigger pattern, not per-child observation** — per-child observation only produces a clean sequential stagger when every staggered element is at the same scroll position.
